# RH-29 MACHINE1-X

MACHINE1-X is an evidence-only progression from W.

- W observed the low-vector copy loop at 0x2340–0x234C successfully writing 0x00–0x1C and then attempting an aligned 32-bit write at 0x20.
- X expands the ROM-seeded mutable low-vector shadow by exactly one observed word: 0x00–0x23 (36 bytes).
- 0x24 and above remain fail-closed. X does not create a broad low-memory mapping.
- X does not assign semantics to 0x0C150004 and does not call it a remap register.
- The RH-29 Machine Probe entry is made visible unconditionally in the More menu; the probe backend still rejects a current device that is not RH-29.
- The expected next device observation is whether the copy loop reaches 0x24 and fails there, or another earlier transition changes control flow/state.


CI retrigger after X contract alignment: controller tests and static contract now match the evidence-gated 36-byte shadow and always-visible Probe UI; RH-29 enforcement remains in the backend.

## Device result: RH29_MACHINE1_X.txt

X on the iPhone executed 1,549 instructions and stopped on a 32-bit write of zero at address `0x00000024`, PC `0x00002344`, LR `0x000003C8`. The write at `0x20` succeeded. The unresolved cause is `rom_write`; the shadow still ends at `0x23`. The R2 value at the stop is `0x2800031D`, after nine loop decrements. This confirms the X gate and rules out advancing the shadow one word at a time as a meaningful solution.

### Exact R2 provenance

The X trace and RH-29 V04.10 ROM bytes agree at every instruction below:

| PC | Instruction | Observed effect |
| --- | --- | --- |
| `0x03B8` | `MOV r1,r11` | `r11=0`, so `r1=0` at the call |
| `0x03C4` | `BL 0x12EC` | enters the sizing routine |
| `0x12EC` | `LDR r2,[r1]` | low-address data read returns `0xEA0000C9` |
| `0x12F0` | `MOV r2,r2,LSL #4` | `0xA0000C90` (32-bit arithmetic) |
| `0x12F4` | `ORR r2,r2,#8` | `0xA0000C98` |
| `0x2334` | `ADD r2,r2,#3` | `0xA0000C9B` |
| `0x2338` | `MOVS r2,r2,LSR #2` | `0x28000326` words |
| `0x2340–0x234C` | `LDR/STR/SUBS/BNE` | copies low words until fail-closed write at `0x24` |

The count corresponds to `0xA0000C98` bytes. It is derived directly from interpreting an ARM branch instruction as data at `[0x00]`; it is not a measured RAM size or permission to map that much memory.

ROM authority: user-supplied `RH-29_QD_V04.10_SYM-ROM.zip`, extracted `SYM.ROM`, SHA-256 `4824ee55086cade3415c7478ec54b9654658bfdd737e779995dfe0ef716ab70b`. Its words at offsets `0x00`, `0x20`, and `0x24` are respectively `0xEA0000C9`, zero, and zero. Source authority: `strict_bus` seeds the 36-byte low shadow from ROM in `machine1/src/rh29_machine_model.cpp`; its read path selects that shadow before the ROM alias. X's low-page log contains no write to word zero before PC `0x12EC`. Therefore the **emulator-side provenance** of the returned word is confirmed. The correct RH-29 hardware-side data view at this point remains unknown.

### Limits and next evidence gate

The Nokia RH-29 service schematic identifies UPP and memory components, but does not define the CPU address map or the effect of the observed write at `0x0C150004`. The public Symbian kernel `bootmain.s` and `bootutils.s` describe generic startup, RAM-bank probing, and copy routines; they are not this RH-29 board support package. Neither source licenses a remap trigger, a replacement value for `[0x00]`, or a broad writable low mapping.

The next model change requires board-specific evidence for the low-address **data** backing and transition, or an independent hardware trace at the same boot stage. Until then keep X unchanged: no `0x24` expansion, no fabricated `[0x00]` response, no remap interpretation for `0x0C150004`. A further on-device diagnostics build that repeats X's R2 and bus trace would not answer the missing hardware question.

References: Nokia RH-29 service schematic, https://manualmachine.com/nokia/ngage/3834739-schematic/ ; Symbian kernel source, https://github.com/SymbianSource/oss.FCL.sf.os.kernelhwsrv/tree/master/kernel/eka/kernel/arm .

## Follow-up ROM disassembly: Dyncom FIQ register banking is the upstream blocker

The X report's `[0x00]` value is a downstream effect of losing the SVC-mode R11. Disassembly of the same V04.10 ROM and X's earlier low-page trace establish:

1. At `0x0344–0x0350`, the firmware obtains a descriptor table at `0x744`. At `0x03D4/0x03E0`, it reads the table count `16` and first entry key `1`; the equality return at `0x03E8` leaves R11 pointing to `0x744`. X captures SVC R11=`0x744` at `0x037C`.
2. At `0x0380`, `BL 0x23E4` finds the descriptor for the `0x0A000000` RAM probe and calls `0x2480`. The routine at `0x2494` executes `MSR cpsr_fc,r3` to enter FIQ; `0x24A8 MOV fp,#0` then writes **FIQ R11**, and the routine eventually returns to SVC through a status-restoring `MOVS pc,sp` at `0x24FC`.
3. At `0x03B8 MOV r1,fp`, X then sees R1=`0` at `0x03BC`, although the earlier SVC R11 was `0x744`. The loss occurs across the FIQ round trip, before `0x12EC LDR r2,[r1]` reads the ROM branch at address zero.

In pinned upstream EKA2L1 `c5ae62d9c667f6e7060d76be58a2614122a629a4`, `ARMul_State::ChangePrivilegeMode()` in `src/emu/cpu/src/dyncom/armstate.cpp` saves SVC R13/R14 when entering FIQ, and saves FIQ R8–R14 when leaving FIQ. It loads FIQ R8–R14 on entry, but **never saves nor restores the shared non-FIQ R8–R12**. The state has `Reg_firq[7]` and no shared R8–R12 bank. ARM's register model requires FIQ's R8–R12 to be separate from the R8–R12 used by SVC. Thus this source behavior explains the exact observed R11=`0` after returning to SVC. The same implementation appears in the currently fetched upstream master, but the pinned SHA is the authority for this build.

**Conditional prediction, not a device observation:** With correct bank preservation and the observed SVC R11=`0x744`, the guest would read `[0x744]=0x10`. The same `0x12EC–0x2338` arithmetic would produce a byte count `0x108`, or R2=`0x42` words. This does not itself authorize writes beyond `0x23`; X should still fail closed at `0x24` until the corrected CPU behavior is measured and the intended low-memory destination is established. It does mean the earlier concern about an unspecified hardware data view at address zero is no longer the first issue to fix.

Next isolated experiment: correct FIQ/shared R8–R12 banking in Dyncom; test SVC→FIQ→SVC preservation and FIQ independence; keep X's bus responses and 36-byte low shadow unchanged; then run a new named device probe to observe the actual R1/R2 and next barrier. Do not patch `[0x00]` or assign meaning to `0x0C150004`.
