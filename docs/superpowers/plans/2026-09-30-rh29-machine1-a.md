# RH-29 MACHINE1-A Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first iPhone-runnable Nokia N-Gage QD RH-29 full-machine probe that starts from the real EKA1 ROM restart vector, executes a bounded number of ARM instructions with EKA2L1 Dyncom, and reports the first unresolved memory/MMIO access without altering the existing HLE product path.

**Architecture:** Keep `hybridhome-upstream1` untouched and implement MACHINE1-A only on `ngage-machine1`. Store the machine model and iOS integration sources in the controller repo, copy/patch them into the pinned upstream checkout during CI, and use a dedicated RH-29 bus wired directly to a fresh `arm::core`; the normal `eka2l1::system`, kernel, services, and `memory_system` are not reused by the probe.

**Tech Stack:** C++17, EKA2L1 `arm::core` / Dyncom, Objective-C++, SwiftUI, Python 3 patch tooling, GitHub Actions macOS 26 / Xcode 26.

**Spec:** `docs/superpowers/specs/2026-09-30-rh29-machine1-design.md`

## Global Constraints

- Product baseline remains `hybridhome-upstream1@acb2775a652f44104c841a6ed08557801a3aadbe`.
- Research work lives only on `ngage-machine1`.
- Upstream source baseline remains `EKA2L1/EKA2L1@c5ae62d9c667f6e7060d76be58a2614122a629a4`.
- Existing HYBRIDHOME3, VPL import, Vietnamese localization, RH-29 HLE boot, and game execution paths must remain unchanged.
- MACHINE1-A is opt-in and visible only when the current firmware code is `RH-29`.
- No guessed RH-29 RAM window and no guessed MMIO implementation may be added.
- ROM must be mapped from its validated header; expected EKA1 ROM base is `0x50000000`.
- Initial ARM reset CPSR is `0x000000D3` (Supervisor mode, ARM state, IRQ/FIQ masked); PC comes from the ROM header `restart_vector`.
- Strict unresolved-access policy is authoritative for MACHINE1-A: stop at the first access outside mapped ROM.
- No LCD, keypad, audio, MMC, timer, IRQ/FIQ delivery, GSM, Bluetooth, or RM-356 full-hardware work in this plan.
- Every CPU run has a finite instruction budget.
- Failure must return a report to SwiftUI and must not crash, mutate, or replace the active HLE device session.

## Review Focus

1. **Malformed/truncated ROM header** — parser must reject files shorter than 512 bytes and report a deterministic parse error. Covered by Task 1 tests.
2. **ROM range overflow / boundary crossing** — `rom_base + rom_size` and bus reads must not wrap or read beyond the supplied file. Covered by Task 1 tests.
3. **Wrong device / wrong ROM** — iOS bridge must refuse the probe unless current firmware is exactly `RH-29`, and parser must reject a non-`0x50000000` ROM base. Covered by Tasks 1 and 4 tests.
4. **First access is a write or code fetch outside ROM** — tracer must preserve access type, width, address, PC, LR, and write value and stop once. Covered by Task 1 tests.
5. **Probe fails or hits CPU exception** — UI must surface the stop reason/report and keep the existing emulator usable. Covered by Tasks 3 and 4 static/integration checks plus final device test.

- [ ] **Step 5: Implement real `run_probe`**

Execution rules:
- read the whole ROM file into an immutable byte vector;
- parse/validate with Task 1;
- create a fresh Dyncom exclusive monitor and CPU via `arm::create_exclusive_monitor(arm_emulator_type::dyncom, 1)` and `arm::create_core(..., arm_emulator_type::dyncom)`;
- wire normal reads, writes, code reads, and exclusive monitor accesses to the dedicated strict bus;
- initialize all GPRs deterministically to zero;
- set CPSR = `0x000000D3`;
- set PC = header `restart_vector`;
- execute in bounded chunks, never beyond `instruction_budget`;
- stop immediately on the first strict-bus unresolved access or CPU exception;
- collect R0-R12, SP, LR, PC, CPSR and executed instruction count before returning;
- never call `eka2l1::system::reset`, kernel scheduler, service manager, VFS mounts, or the active HLE CPU.

- [ ] **Step 6: Add build-time contract for the real runner**

The later CI workflow must compile the real runner inside the iOS target against upstream `cpu`. The contract is satisfied only when Xcode links the new source into the app.

## Self-Review

- **Spec coverage:** Tasks 1-6 cover ROM parsing, ROM-only bus, real restart vector, bounded ARM execution, strict unknown-access tracing, iOS-only RH-29 gating, report export, branch isolation, build, and device evidence. Synthetic-zero mode is intentionally deferred because MACHINE1-A's authoritative criterion is strict first-access discovery.
- **Step scan:** Each implementation task follows RED → minimal implementation → GREEN → commit. Device testing is separated from implementation and cannot silently authorize a hardware stub.
- **Type consistency:** Task 1 types feed Task 2; Task 2 returns a formatted result through the Task 4 Obj-C/Swift report wrapper; Task 5 compiles exactly those files.
- **Review Focus:** All five risks are assigned to concrete tests/checks above.
- **Proportion:** The plan fixes interfaces and verification points but leaves implementation bodies to the executor; it does not prescribe speculative RAM/MMIO behavior.
